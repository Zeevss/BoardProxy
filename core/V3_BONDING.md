# BoardProxy v3: bonded transport

## Цель

Одно логическое подключение (`Bundle`) может использовать несколько физических
каналов (`Lane`). Каждый lane по-прежнему является парой
`board.Session -> link.Link` на отдельной странице. Один `mux.Session` работает
поверх всего bundle, поэтому байты одного TCP-стрима в будущем смогут идти по
разным страницам.

Термины:

- **Bundle** — одно логическое подключение клиента к серверу;
- **Lane** — одна физическая board-сессия на одной странице;
- **BundleID** — случайный 128-битный идентификатор bundle;
- **LaneID** — идентификатор lane внутри bundle;
- **PacketID** — идентификатор bond-пакета для ACK, дедупликации и retransmit;
- **Epoch** — поколение bundle после полного переустановления соединения.

## Почему bond-ACK не должен стать дорогим

`link` уже подтверждает каждый объект удалением со страницы. Поэтому первая
реализация не должна создавать второй ACK-объект поверх каждого bond-пакета.
Вместо этого `link.Send` будет расширен delivery receipt: bond свяжет свой
`PacketID` с board-объектом и получит уведомление о существующем delete-ACK.
Неподтверждённый PacketID останется в replay buffer и после потери lane будет
отправлен через другой lane. Получатель дедуплицирует повтор по PacketID.

Если live-тесты покажут, что delete-ACK приходит раньше безопасного принятия
пакета bundle-очередью, вводится отдельный endpoint ACK. Но и тогда v3 должен:

1. подтверждать диапазоны `PacketID`, а не каждый пакет отдельно;
2. задерживать ACK на короткое ограниченное время и объединять соседние ACK;
3. piggyback-ить ACK на обратный трафик;
4. создавать отдельный ACK-пакет только при отсутствии обратного трафика;
5. выполнять retransmit только после потери lane или RTO, а не по таймеру
   каждого link-объекта;
6. ограничивать память общим `max_unacked_bytes`.

ACK уровня `link` остаётся источником RTT и congestion-control конкретного lane.
Он же по возможности используется как bond delivery receipt. PacketID в bond
envelope всё равно обязателен: ACK страницы мог потеряться вместе с lane уже
после доставки, поэтому retransmit должен быть безопасно дедуплицирован.

## Инварианты

1. Потеря одного lane не закрывает mux и его TCP-стримы.
2. Повторная доставка bond-пакета не дублирует TCP-байты или UDP-датаграмму.
3. DATA одного TCP-стрима выдаётся egress строго по `StreamOffset`.
4. `FIN(final_offset)` становится EOF только после доставки всех предыдущих
   байтов.
5. Flow-control сообщения идемпотентны: v3 использует абсолютный
   `MAX_STREAM_DATA`, а не аддитивный credit.
6. Каждый lane получает независимые traffic keys и пространство nonce.
7. Дополнительный lane криптографически привязан к BundleID, а не только к
   пользовательскому ключу.
8. Сервер ограничивает lane по bundle, пользователю и доступному пулу страниц.
9. Открытие нового lane сериализовано; одновременно выполняется не больше одного
   `JOIN_LANE`.
10. Закрытие lane сначала переводит его в `draining`; Bundle GOAWAY закрывает
    всё логическое подключение.

## Метрики регулятора

Первая реализационная стадия добавляет метрики без изменения wire protocol:

- `transport_acked_bytes` — байты link-payload, подтверждённые пиром;
- `backlog_frames` и `backlog_bytes` — текущая очередь mux на отправку;
- `blocked_writers` — количество writers, остановленных полной очередью mux;
- `inflight`, `effective_limit`, RTT и `target_batch_size` — состояние lane.

Сам по себе выход `target_batch_size` на плато не является сигналом scale-up.
Lane открывается после двух секунд устойчивого спроса: непустой очереди,
заблокированного writer либо upload/download не меньше 512 KiB за секунду.
После успешного расширения следующий lane разрешён через 3 секунды. Это
намеренно простой регулятор: он быстро расширяет активную передачу до клиентского
лимита, не пытаясь угадать marginal gain на коротком и шумном интервале.
Сервер независимо применяет свой лимит; отказ `JOIN_LANE` включает backoff.

## Этапы

Текущее состояние:

- этап 0 завершён;
- control-plane часть этапа 1 завершена для `NEW_BUNDLE`;
- transport-подстадии 2A, 2B и этап 3 завершены;
- production-клиент начинает с одного lane и при устойчивой передаче
  присоединяет дополнительные board-сессии через `JOIN_LANE` до настроенного
  клиентского и серверного лимита;
- оба lane работают через один `bond.Conn -> mux.Session`; сервер создаёт один
  egress на bundle, а не по egress на страницу;
- потеря одного lane освобождает только его страницу, переносит unacked-пакеты
  на оставшийся lane и не закрывает mux;
- если дополнительный lane нельзя выделить, подключение продолжает работать
  через уже активные; лимит настраивается отдельно на клиенте и сервере;
- management API и panel показывают список lane внутри логического подключения.
- bond использует PacketID только для dedup/replay и выдаёт пакеты сразу, не
  ожидая пропущенный PacketID с другого lane;
- TCP DATA несёт `StreamOffset`, FIN — `FinalOffset`, а flow control использует
  абсолютный `MAX_STREAM_DATA`; каждый stream независимо собирает свои диапазоны
  и увеличивает receive window от 1 MiB до настроенного потолка при быстром
  потреблении данных;
- DATA/FIN, обогнавшие SYN на другой странице, временно хранятся в ограниченном
  pre-open буфере; то же правило действует для UDP DATAGRAM до DATAGRAM_OPEN;
- legacy v2 mux остаётся на упорядоченном link и additive WINDOW_UPDATE.
- offset-wire использует protocol v4; сервер сохраняет ordered compatibility
  mode для ранее собранных bonded v3 клиентов. Обновлять нужно server-first.

### Этап 0. Наблюдаемость без изменения протокола

- экспортировать подтверждённые link-байты;
- экспортировать mux backlog и blocked writers;
- добавить значения в debug-логи и клиентские метрики;
- сохранить `proto.Version == 2`;
- покрыть счётчики unit/race-тестами.

### Этап 1. Bundle rendezvous

- поднять wire version 3 с явным negotiation;
- добавить BundleID/LaneID/Epoch;
- расширить аутентифицированный handshake payload на `NEW_BUNDLE` и
  подготовить формат `JOIN_LANE`;
- связать lane с bundle через аутентифицированный handshake payload;
- хранить на сервере `user -> bundles -> lanes`;
- оставить один lane активным, чтобы отдельно проверить lifecycle.

### Этап 2. Фиксированный двухканальный bond

- ввести bond envelope и PacketID;
- расширить link delivery receipt и сначала переиспользовать существующий ACK;
- хранить unacked payload в ограниченном replay buffer;
- добавить deduplication и retransmit после потери lane;
- при необходимости добавить cumulative endpoint ACK + selective ranges;
- сначала использовать два lane с фиксированными весами.

Подстадии:

- **2A — завершена:** независимый `bond.Conn`, link delivery receipts,
  sequencing, bounded replay/reorder, dedup и retransmit;
- **2B — завершена:** серверный `JOIN_LANE`, присоединение второй реальной
  страницы к существующему bundle, один production mux поверх `bond.Conn`,
  независимое освобождение страниц и деградация до одного lane.

Этап 4 завершён: scheduler оценивает время доставки по RTT и числу inflight,
а простой контроллер добавляет lane после двух demand-сэмплов и выдерживает
трёхсекундный интервал между успешными расширениями. Спрос учитывает исходящую
очередь и фактический upload/download, поэтому скачивание тоже запускает
scale-up. Отказ `JOIN_LANE` (лимит или исчерпанный pool) включает 15-секундный
backoff без отдельного wire-сообщения.

### Этап 3. Полосование одного TCP-стрима — завершён

- поднять negotiated wire version до 4, сохранив серверную совместимость с v2/v3;
- добавить DATA StreamOffset;
- заменить WINDOW_UPDATE на абсолютный MAX_STREAM_DATA;
- добавить FIN FinalOffset;
- реализовать ограниченный per-stream reorder buffer;
- тестировать reorder, duplicate, partial loss и ранний FIN.

### Этап 4. Адаптивное управление — завершён

- weighted earliest-delivery scheduler по `RTT * (inflight + 1)`;
- один `JOIN_LANE` за раз после двух устойчивых demand-сэмплов;
- интервал 3 секунды между успешными scale-up;
- scale-down после 30 секунд простоя через draining;
- устойчивый upload/download от 512 KiB за сэмпл запускает scale-up;
- `JOIN_LANE` denial используется как server-pressure hint с backoff 15 секунд;
- receive window каждого активного stream удваивается при быстром потреблении,
  начиная с 1 MiB и до `max_stream_window` (по умолчанию 32 MiB);
- отдельный proactive wire-hint от сервера пока не вводится.

### Этап 5. UDP и эксплуатация

- отправлять датаграмму целиком через один lane;
- DatagramID и deduplication;
- bundle/lane метрики в management API;
- квоты, graceful shutdown, partial reconnect и live-тесты.

## Настройка лимита lane

- клиент CLI: `bproxy connect --max-lanes 4 ...`;
- клиентский TOML: `max_lanes = 8`;
- переменная клиента: `BPROXY_MAX_LANES=4`;
- сервер CLI: `bproxy serve --max-lanes 4 ...`;
- переменная сервера: `BPROXY_SERVER_MAX_LANES=4`.

Допустимый диапазон — от 1 до 32, значение по умолчанию — 8. Фактическое число
lane не превысит меньший из клиентского лимита, серверного лимита и количества
свободных страниц.
